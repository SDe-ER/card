# CARD v4.4.3 — 2026-11-09

> Patch release on top of v4.4.2 (PR #180): the PDF button of the Equipment Supplier Statement renders with the
> Frappe Chrome PDF generator on one A4 portrait page, and the statement keeps its font under a site print style.
> Backward compatible: no patch, no DocType or schema change, no change to permissions or accounting; one new POST
> API method.
> Labels: **Verified / Partially Verified / Unknown / Not Supported / Deprecated / Removed**.

## 1. Version Overview

The v4.4.2 post-deploy check on 2026-11-09 found two print faults. The owner kept v4.4.2 and asked for them to be
fixed forward:

- the PDF button of the report used frappe `report_to_pdf`, which always renders with wkhtmltopdf. On the server's
  wkhtmltopdf 0.12.6.1, the Arabic alef after a joining letter is printed in the wrong form ("حساب", "الصافي"). With
  the default Landscape orientation the signatures moved to a second page;
- a site print style that sets the font of every print element with `!important` replaced the statement font in
  the browser print.

Why a patch version: a correction of one report's print output. There is no new capability and no schema change.

## 2. Complete Feature Inventory — Verified

Everything in [v4.4.2](v4.4.2.md) is present (code at the tag). The changes:

| Component | Change |

It runs the standard `frappe.desk.query_report.run` with the report's Link filters, builds the page on the server with the CSS of the print template, and renders it with `frappe.utils.pdf.get_chrome_pdf`. | report `equipment_supplier_statement.html`, print format `equipment_supplier_statement_a4` | Page A4 portrait; signatures and issued-by line kept together on one level; font rule `!important` and more specific than `.print-format *` |
| `card/locale/ar.po`, `card/locale/main.pot` | Arabic for the three new messages |
| `card/tests/test_supplier_statement_pdf.py` (new), `test_supplier_statement_print.py` | Endpoint, permissions, escaping, portrait page, font rule |

## 3. Added

## 4. Improved

- The statement PDF prints on one A4 portrait page for a normal period. The signatures and the issued-by line stay
  with the totals.

## 5. Fixed — Partially Verified

- Arabic letters join in the statement PDF (Chrome generator). This was shown on Production by one render-only
  call before the merge: 1 page, A4 portrait, NotoSansArabic embedded, "حساب" and "الصافي" joined, title not
  clipped, Western digits. The download from the deployed button is **Unknown** until the post-deploy check
  (section 12).
- The statement font is no longer replaced by a site print style in the browser print. This was shown in the
  browser on Production with the new rules injected client-side.

Nothing removed.

## 7. Replaced

- The PDF path of this report: frappe `report_to_pdf` (wkhtmltopdf) → `download_pdf` (Chrome generator).
- The page of the A4 supplier statement: A4 landscape → A4 portrait.

## 8. Simplified

Nothing simplified.

## 9. Breaking Changes — Verified

None for data, schema or permissions. The PDF dialog's letter head and orientation are not used by this report's
PDF, which is always the fixed A4 portrait statement. A user with report access but without print permission on
Card Monthly Card cannot download the PDF; this is the same condition as the standard PDF menu item.

## 10. Known Limitations — Verified

- **Published ≠ deployed.** Deployment of 4.4.3 to any site is a separate, site-verified fact (section 14).
- The PDF needs a working Chrome PDF generator on the site, the same one the CARD document prints use since
  v4.4.1. If it is missing, the endpoint shows an error and no PDF is produced.
- The PDF page is built on the server from the same CSS as the browser print, but its markup is a Python copy of
  the browser template. A future layout change must update both, and the tests check each of them.
- English print: **Unknown** (not checked on a site).
- A period with many cards prints on several pages.

## 12. Installation & Upgrade — Partially Verified

`bench --site <site> migrate` runs no new patch and changes no DocType. It re-imports only the standard Print
Format `Equipment Supplier Statement A4` (file `modified` 2026-11-10 10:00, newer than the v4.4.2 row). It writes
no value to cards, transports, fills, postings or settings, and no GL entry. Restart the web and background workers
after the code update. Compile the CARD translations (`ar`) into the image as in previous deployments.

**Post-deploy check (required):** for one supplier, use the report's PDF button and the browser Print, in Arabic.
Check: one A4 portrait page, Arabic letters joined, title not clipped, Western digits, Noto Sans Arabic, signatures
on one level, issued-by line. Also check the Error Log for new rows.

**Rollback statement — Partially Verified** (the frappe import rules are those recorded for v4.4.0 to v4.4.2; the
commands were not rehearsed on a site).

- Last stable version: **v4.4.2**.
- Data: the v4.4.2 code runs on the v4.4.3 database. There is no schema change.
- Print format: checking out v4.4.2 and running `bench migrate` does **not** restore the v4.4.2 A4 format, because
  its file is older than the v4.4.3 row. Re-import it with `force` after the owner's approval and a verified backup:
  ```
  bench --site <site> execute frappe.modules.import_file.import_file_by_path \
    --kwargs '{"path": "<bench>/apps/card/card/card/print_format/equipment_supplier_statement_a4/equipment_supplier_statement_a4.json", "force": True}'
  ```
- After a rollback, the PDF button uses wkhtmltopdf again (v4.4.2 behaviour).
