# CARD v4.4.1 — 2026-11-09

> Patch release on top of v4.4.0 (PR #175): display fixes found in the v4.4.0 production check. The CARD document
> prints use frappe's Chrome PDF generator, because wkhtmltopdf broke Arabic letter joining in their PDF, and the
> A4 supplier statement prints a short statement of totals. Backward compatible: no patch, no DocType or schema
> change, no change to permissions, accounting, data or the API (the report summary items gain an added `key`
> field).
> Labels: **Verified / Partially Verified / Unknown / Not Supported / Deprecated / Removed**.

## 1. Version Overview

The v4.4.0 production check (2026-11-09) found two display problems:

- The PDF of the CARD document prints, made with wkhtmltopdf, broke Arabic letter joining (an alef after a
  joining letter printed detached). frappe's Chrome PDF generator printed Arabic correctly on the same site. The
  four standard document formats (`Card Monthly Card Print`, `Equipment Transport Print`,
  `Project Diesel Fill Print`, `Tool Handover Receipt`) and the fixture `كارت تشغيل شهري` now set
  `pdf_generator` to `chrome`.
- The A4 supplier statement printed every reconciliation figure. The print now keeps a short statement:
  opening balance + period charges (incl. VAT) − payments = closing balance (with ledger access), the card net
  (without), or equipment / days / hours (owned equipment). The reconciliation figures and notes stay on the
  screen report. The print picks the figures by a stable summary `key`, whatever the language, and the closing
  balance is rounded from the rounded opening, charges and payments so the printed lines add up to the cent.

Why a patch version: corrections of the v4.4.0 print output; no new capability, no schema change.

## 5. Fixed — Partially Verified

- Arabic letter joining in the PDF of the CARD document prints: the Chrome PDF generator replaces wkhtmltopdf for
  the four document formats and the fixture (FR-055, FR-045; PR #175). The defect was seen on Production in the
  v4.4.0 check; the fix is shown by the format setting and a test, and the Chrome generator printed a standard
  Sales Invoice correctly on Production during the same check. A CARD print through Chrome on Production is not
  yet checked (section 10).
- Printed totals of the A4 supplier statement add up to the cent: the closing balance is rounded from the rounded
  opening, charges and payments (FR-089; PR #175; `test_report_access.py`).

## 6. Removed

Nothing removed. The reconciliation figures (accrual vs. invoiced through Card, invoices outside Card) and the
reconciliation notes are no longer printed on the A4 supplier statement; the screen report keeps them and no data
is removed.

## 7. Replaced

- The printed totals block of the A4 supplier statement is replaced by the short statement (same data, fewer
  lines) (FR-089; Owner request 2026-11-09).
- The PDF generator of the four CARD document formats and the fixture: `wkhtmltopdf` → `chrome`.

## 8. Simplified

- The A4 supplier statement prints four total lines (opening, period charges, payments, closing) instead of the
  full reconciliation.

## 9. Breaking Changes — Verified

None. No schema, permission, accounting, data or API change; the print formats keep their names. The report
summary keeps its labels and values and only gains a `key` per item. A client that read the printed
reconciliation figures from the A4 PDF must use the screen report.

## 10. Known Limitations — Verified

- **Published ≠ deployed.** Deployment of 4.4.1 to any site is a separate, site-verified fact (section 14).
- The PDF button of the A4 supplier statement still renders with wkhtmltopdf: frappe `report_to_pdf`
  (`frappe/utils/print_format.py`) always uses wkhtmltopdf for report prints, so that PDF can still break Arabic
  letter joining. The browser Print of the report is not affected; use it for Arabic.
- The Chrome PDF generator must work on the site. On Production it printed a standard Sales Invoice correctly
  during the v4.4.0 check (2026-11-09): **Partially Verified**. A printed PDF of each CARD document format with
  Chrome on a real site: **Unknown** until the post-deploy print check (section 12).
- As in v4.4.0: names stored in the data print as stored; in a language without a CARD catalogue the
  CARD-specific labels print in English; choose Landscape in the PDF dialog of the A4 supplier statement.
- Rolling back the code alone does not restore the v4.4.0 print formats (section 12).

## 12. Installation & Upgrade — Partially Verified

`bench --site <site> migrate` runs no new patch (`card/patches.txt` unchanged) and changes no DocType. It
re-imports the five standard Print Formats (`Card Monthly Card Print`, `Equipment Transport Print`,
`Project Diesel Fill Print`, `Tool Handover Receipt`, `Equipment Supplier Statement A4`; file `modified`
2026-11-09 16:10, newer than the v4.4.0 rows) and the Print Format fixture `كارت تشغيل شهري`
(`frappe.utils.fixtures.sync_fixtures` imports fixtures with `force`). It writes no value to cards, transports,
fills, receipts, postings, GL Posting Logs or settings, and no GL entry. The report summary `key` is computed when
the report runs; nothing is stored.

Restart the web and background workers after the code update (normal for an image deploy). Compile the CARD
translations (`ar`) into the image as in previous deployments; without them the new label prints in English.

**Post-deploy check (required):** print one document of each CARD format (`Card Monthly Card Print`,
`كارت تشغيل شهري`, `Equipment Transport Print`, `Project Diesel Fill Print`, `Tool Handover Receipt`) to PDF and
check the Arabic letter joining; print the A4 supplier statement with the browser Print and check the short
totals.

**Rollback statement — Partially Verified** (the frappe import rules are those recorded for v4.4.0, read in
frappe `version-16` source, 16.55.2; the commands were not rehearsed on a site).

- Last stable version: **v4.4.0** (runs on Production since 2026-11-09, image tag `card-v4.4.0-...`; the
  deployment record is pending in PR #174).
- Data: v4.4.0 code runs on the v4.4.1 database. There is no schema change; the extra summary `key` is not stored
  and v4.4.0 does not use it.
- Print formats: checking out v4.4.0 and running `bench migrate` does **not** restore the five v4.4.0 standard
  Print Formats, because their files (`modified` 2026-11-09 14:00 / 13:30) are older than the v4.4.1 rows and
  `import_file_by_path` skips them unless `force` is set. Until they are re-imported the four document formats
  stay on `chrome` (they render with v4.4.0 code, which registers `card_print_is_rtl`), and the A4 format keeps the
  v4.4.1 template, which looks for summary keys v4.4.0 does not send (Unknown: not tested under v4.4.0 code).
- The fixture `كارت تشغيل شهري` returns to its v4.4.0 content (`wkhtmltopdf`) on that migrate (fixtures are
  imported with `force`).
- Steps, after the owner's approval for the rollback and a verified backup:
  1. Deploy the v4.4.0 code (image) and restart the workers.
  2. `bench --site <site> migrate` (restores the fixture; changes nothing else).
  3. Re-import each of the five standard formats from the v4.4.0 files with `force`:
     ```
     bench --site <site> execute frappe.modules.import_file.import_file_by_path \
       --kwargs '{"path": "<bench>/apps/card/card/card/print_format/<name>/<name>.json", "force": True}'
     ```
     for `<name>` = `card_monthly_card_print`, `equipment_transport_print`, `project_diesel_fill_print`,
     `tool_handover_receipt`, `equipment_supplier_statement_a4`. Write `True` (Python), not `true`.
  4. Open each print once to check it renders.
- Alternative: restore the pre-upgrade database backup, only while no data was entered after the backup;
  otherwise use the forced re-import, which touches only Print Format rows.
