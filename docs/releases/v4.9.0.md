Release page for CARD v4.9.0. Required by the [Release Documentation Policy](RELEASE-POLICY.md) and the
[Change, Versioning & Safe Rollback Policy](../governance/CHANGE-VERSIONING-ROLLBACK-POLICY.md).

> pushed). It does not say that any site runs it. Deployments are recorded in [DEPLOYMENTS.md](DEPLOYMENTS.md).

**Partially Verified** (the evidence covers part of the claim), **Unknown** (no evidence either way), **Not Supported**,
**Deprecated**, **Removed**.

## 3. Added

- **FR-166 — Volume billing per m³ and per load (customer side).** Equipment and card can use the per-m³ rate type; the
  customer amount is loads × load volume (m³) × rate per m³, before VAT. Hours are still recorded and are not billed on
  this basis. New fields: `load_volume_m3` (equipment), `loads_count` (day), `total_loads`, `total_volume_m3`
  (permlevel 1), `load_volume_used`. New whitelisted read endpoint `loads_last_month` (POST). Dashboard number card
  "Loads last month". Non-blocking warning for a per-m³ card with hours and no loads. Source: CHANGELOG section 4.9.0
  and PR #258 (merged `9b08457`). Verified.
- **FR-167 — Review copy print for unapproved Card Monthly Cards.** An unapproved card (docstatus 0) prints a banner
  "Review Copy — Not Approved", a meta line (workflow state, printed by, printed at) and a light "REVIEW COPY" watermark.
  Submitted cards print as before. Money gating is unchanged. PR #268 (merged `69d7135`). Verified (tests run in CI).
- **Docs — CI-generated screenshots (manual workflow `docs-screenshots.yml`).** Not a pull request check; it deploys
  nothing. PR #267 (merged `fc4de58`). Verified.

## 9. Breaking Changes — Verified

No API is removed and no existing amount changes on migrate. The behaviour changes below apply by default to any
site that moves from v4.7.0 to v4.9.0. They come from v4.8.0 (section 9 of its page) and from v4.9.0.

- **From v4.8.0 (FR-133, FR-134, FR-148, FR-153, FR-146, FR-137, FR-144 and others):** see
  [v4.8.0 section 9](v4.8.0.md#9-breaking-changes--verified). Company-restricted users see only their own companies'
  Card Settings rows; `min_hours` is hidden and read-only; a child row cannot be forged to another document; the
  per-hour rate takes precedence when an equipment has both a per-hour and a daily rate.
- **From v4.9.0 (FR-166):** a card or equipment with the per-m³ rate type can be saved only by code that has the option
  (this release and later). Older code refuses the save of such a document (see section 12).
- **From v4.9.0 (FR-167):** the title of an unapproved card's print changes (banner, meta line, watermark; the "(Draft)"
  label is replaced).

## 10. Known Limitations — Verified

- A draft card or equipment with the per-m³ rate type cannot be saved by the v4.7.0 code (section 12).
- The legacy Arabic print format "كارت تشغيل شهري" still prints drafts without the review banner; only the standard
  format "Card Monthly Card Print" shows it. Verified in the fixture.
- "Printed by" shows the session user; a print made by a background job shows the system user. Documented in FR-167.
- The "Loads last month" number card reaches a site through the fixture on migrate. The number card calls a method that
  exists only in v4.9.0 (section 12).
- No Production or site runtime check is part of this release page. Runtime evidence for each feature is in the PR
  checks of the merged pull requests and in the post-deployment record of the site that installs it (not in this
  repository).

### Upgrade steps (for the operator; run on a verified backup)

1. Verify the backup (database and files) before the change, per the policy.
2. Deploy the v4.9.0 image or code.
3. Run `bench migrate` once, then again; the second run must make no change.
4. Check: submitted-card amounts identical before and after; posting and ZATCA unchanged; no feature switched on that is OFF
   in section 2.

### Safe rollback — Verified from source; not runtime-tested

The rollback target is **v4.7.0, commit `e566174`** (the last recorded Production version). A rollback restores the
**code only**. It does not restore the database. The analysis below is from the frappe `version-16` source and the CARD
source at `origin/main`; it has not been run on a site.

- **Stored amounts:** submitted cards keep their stored `net_amount` and `customer_net_amount`. Posting and cancel read
  those stored values. The old code does not reprice them (verified: `gl/posting.py` reads the stored totals).
- **Drafts:** migrate does not reprice drafts. A draft whose rate type is the per-m³ value cannot be saved by the old
  code, because Frappe checks Select values against the DocType options at save time (`frappe/model/document.py`,
  `_validate_selects`). Load does not reject the value.
- **New fields:** the old code reads the database with `SELECT *` and writes only the fields of its own DocType.
  The new columns are kept and not overwritten (verified in `document.py` and `meta.py`).
- **New DocTypes from v4.8.0:** the old code removes their DocType records (`remove_orphan_doctypes`); their tables
  are kept (reasoned, not run).
- **Patches:** nothing is re-run or reversed; Patch Log rows stay.
- **Fixtures:** the old fixtures are re-imported, so the Workspace and the print format return to the v4.7.0 versions.
  The "Loads last month" number card stays in the database and would likely fail when rendered, because the method is not
  in v4.7.0 (reasoned).
- **Accounting:** the rollback writes no GL entry, Purchase Invoice or Sales Invoice.

**Rollback procedure (owner approval required for each step):**

1. Before the rollback, set the rate type of every draft card and every equipment that uses the per-m³ value to a valid
   option (or leave it and accept that the draft cannot be saved by the old code).
2. Stop the site, check out the v4.7.0 code (`e566174`), and run `bench migrate` once.
3. Verify the amounts of the submitted cards are unchanged and that posting is unchanged.
4. A database restore is allowed only when no transaction was made after the backup. Otherwise the rollback is a
   forward fix. Never restore a database over later Production transactions.
