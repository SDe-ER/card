# CARD v4.11.1 — 2026-11-25

> Patch release on top of v4.11.0: the Card Equipment accounting dimension is created only when Card Settings
> switches it on (FR-180, PR #303), the card money level is checked in seven reports (FR-178 PR #296, FR-179 PR #302,
> FR-181 PR #304), plain additions and deductions save without an Adjustment type (FR-173, PR #285), the Monthly Card
> print says "before VAT" (FR-174 follow-up, PR #292), a period run notices a change of loads (FR-177, PR #294), the
> customer statement has an A4 print (FR-187, PR #312), the hour settings have no number in the code (FR-184, PR
> #309), loads show only on per-m³ cards (FR-186, PR #311), diesel totals say when they include an estimate (FR-185,
> PR #310) and the party portal, which stays off, has two hardening changes (FR-182 PR #305, FR-183 PR #306).
> Backward compatible: three patches, none of which creates a document (Card Settings values only); no role,
> DocPerm or accounting change; one new read-only GET method.
> **Published 2026-11-25** (tag `v4.11.1`, owner approval 2026-11-25). **Published ≠ deployed** (see
> [DEPLOYMENTS.md](DEPLOYMENTS.md)).
> Labels: **Verified / Partially Verified / Unknown / Not Supported / Deprecated / Removed**.

## 3. Added — Verified

- **FR-180 — Card Settings switch "Enable Card Equipment accounting dimension"** (default off). Verified by CI tests
  (`test_card_equipment_dimension.py`).
- **FR-187 — A4 print of Equipment Customer Statement** (Print Format `Equipment Customer Statement A4`). Verified by
  CI tests (`test_customer_statement_print.py`); not yet seen on a real Desk.
- **`get_adjustment_type_names(company)`** (`methods=["GET"]`, read-only; create or write on Monthly Cards and a
  permitted company). Verified by CI tests.

## 4. Improved — Verified

- **Card money level in seven reports (FR-178, FR-179, FR-181).** Equipment Customer Statement, Equipment Customers
  Summary, Equipment Suppliers Summary, Equipment Supplier Statement, Unbilled Card Work, Card Settlement Status and
  Equipment Partial Margin send no figure taken from card amounts to a user whose roles do not read permlevel 1 of
  Card Monthly Card. No role or DocPerm changes; every role of these reports reads level 1 today.
- **FR-174 follow-up — Monthly Card print:** the settlement headers say "before VAT"; the Card totals amounts print
  with the currency.
- **Billed-day helpers:** every caller states whether loads count.
- **FR-184 — Hour settings:** Standard month hours and the two shift limits come only from Card Settings; the
  upgrade stores 260, 12 and 12 where a site had no value, so nothing changes until the owner changes them.
- **FR-185, FR-186:** diesel totals that include an estimate are labelled; loads show only on per-m³ cards.
- **FR-182, FR-183:** party portal hardening (the portal stays off on every company).

## 5. Fixed — Verified (CI); Desk not yet seen

- **FR-173:** a plain addition or deduction saves when no Adjustment type is configured; the optional field is not
  shown then, also for users who saved it as a grid column.
- **FR-177:** a change of loads on a per-m³ card marks a new period run as changed.

## 9. Breaking Changes — Verified

None for sites and API clients. A custom Python caller outside CARD that called `card.transfer.is_billed_day` or
`billed_day_rows` without `include_loads` now gets a `TypeError`. A site that expected v4.11.0's automatic dimension
on upgrade must turn the switch on and run the command.

## 10. Known Limitations — Verified

- While the dimension is off, Equipment Supplier Statement with an Equipment filter does not split payments, VAT and
  other credits by equipment (it says so), and posting stays refused by its preflight.
- Figures of accounting documents stay visible to ledger readers without the card money level (owner decision
  2026-11-24). For an invoiced card they can equal the card amount.
- FR-173, FR-186 and FR-187 are not yet verified on a real Desk (source and CI tests only). The PDF button of the
  customer statement uses the standard PDF generator: if Arabic letters come out unjoined, use Print and "Save as
  PDF" in the browser.
- Dependency scan (Trivy 0.76.2, 2026-11-24): no HIGH or CRITICAL; 5 MEDIUM and 3 LOW in the CARD Mobile build
  tooling (`frontend/yarn.lock`), not changed by this release.
- Everything listed for v4.11.0 that this page does not change.

## 12. Installation & Upgrade — Partially Verified

- **Upgrade from v4.10.1 or v4.11.0:** new code; `bench --site <site> migrate`; `bench --site <site> clear-cache`;
  restart. No `bench build` (no `public/` or `frontend/` change).
- **What migrate writes:** the new Card Settings field (a Single: no column); `depends_on` on three Card Monthly Card
  fields; the changed standard Print Format records and the new one (Equipment Customer Statement A4); up to three
  Card Settings values (standard month hours 260, shift limits 12 and 12) where they are missing or 0; on a site that
  already has the dimension enabled, one more Card Settings value. **It does not write:** an Accounting
  Dimension, a `card_equipment` custom field or column, any document, amount, GL entry, invoice, payment, role or
  permission.
- **Creating the dimension later** is a separate, backed-up step: turn the switch on in Card Settings, then run
  `bench --site <site> execute card.dimension.ensure_card_equipment_dimension`.
- **Post-deployment acceptance (owner, read-only unless stated):** add a plain addition and a plain deduction on a
  draft card and save (FR-173); print a Monthly Card and read the "before VAT" headers; open Equipment Supplier
  Statement with an Equipment filter and read the note; check in Card Settings that the switch is off and that no
  Accounting Dimension "Card Equipment" exists.
- **Safe rollback — Verified from source; not runtime-tested.** Target: the version the site ran before (v4.10.1
  `d58f6b7` for a site that never ran v4.11.0), code only. Older code ignores the new Card Settings value. A period
  run built with fingerprint version 2 fails on older code: cancel and amend such runs after a rollback. The print
  formats keep the v4.11.1 template until they are reloaded from the older JSON. A database restore removes every
  change made after the backup.
