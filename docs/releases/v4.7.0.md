# CARD v4.7.0 — 2026-11-10

> Minor release on top of v4.6.0: five pull requests (#199, #200, #201, #202, #203). One security fix (company checks
> on tool custody, equipment needs requests and reviews), one fix (VAT rate from the company's tax templates), two new
> features (diesel-fill equipment status guard, Equipment Location History report), a role and action matrix with
> cross-company tests, and an architecture documentation pack. No patch, no DocType schema change, no new setting.
> Labels: **Verified / Partially Verified / Unknown / Not Supported / Deprecated / Removed**.

## 1. Version Overview

v4.7.0 collects the work merged to `main` between the v4.6.0 release merge (`87c375d`, PR #205) and `be73af2`
(PR #203). Main themes:

- **Security (first):** a user limited to one company can no longer create, submit, read or change Employee Tool
  Custody, Equipment Needs Request or Equipment Needs Review records of another company; `card.tool_custody.move`
  runs `check_permission("create")` before it reads anything (FR-129).
- **Accounting configuration:** the VAT rate of the CARD item tax templates, the posting preview, the diesel net-back
  and the reconciliation comes from the company's configured purchase and sales tax templates; no hardcoded 15
  (FR-127).
- **Diesel:** the FR-122 equipment status guard now also covers Project Diesel Fill (FR-128, Warn only by default).
- **Reports:** read-only Equipment Location History (FR-130).
- **Governance and documentation:** role and action matrix rendered from and checked by tests (FR-129); architecture
  pack (`docs/architecture/`, #202).

Why a minor version: new capabilities (a report, a guard); no API is removed. The behaviour changes that apply by
default are listed in section 9.

Previous version on Production: **v4.4.3** (`688eb71`, last recorded in [DEPLOYMENTS.md](DEPLOYMENTS.md)). v4.5.0
and v4.6.0 have no recorded Production deployment. At the time of writing v4.6.0 is merged (`87c375d`) but its tag
is not published yet (the latest GitHub Release is v4.5.0). A deployment of v4.7.0 to a site on v4.4.3 also brings
the changes of [v4.5.0](v4.5.0.md) and [v4.6.0](v4.6.0.md); their setup actions and rollback limits apply too.

## 9. Breaking Changes — Verified

No API is removed and no data is changed by the release. These behaviour changes apply **by default**:

- **FR-129 — company-restricted users are refused cross-company custody, request and review records.** A user with a
  Company User Permission that does not cover every company cannot read, create (also through REST with
  `docstatus` 1), save, submit or cancel an Employee Tool Custody whose stored company or whose employee or receiving
  employee belongs to another company, an Equipment Needs Request whose stored company or equipment belongs to another
  company, or an Equipment Needs Review whose stored company or project belongs to another company. `move` (the Tool
  Custody screen) refuses an employee of another company before it reads the worker's machines. Users without a
  Company User Permission, or with one that covers every company, and Administrator are not affected. Existing records
  are not changed.
- **FR-127 — a hand-edited template rate is refused.** CARD never changes the rate rows of an existing item tax
  template. The preflight refuses a linked "CARD VAT" item tax template whose rows do not all carry the company's
  standard rate ("Item tax template {0} must carry a flat {1}% rate."); `_reconcile_item_tax_template` refuses to
  re-point a template that does not carry the rate ("... CARD never changes the rate of an existing template."); a
  built draft whose line VAT or total taxes changed since CARD built it (for example after a hand edit of the item
  tax template, which ERPNext re-applies on every save) is refused on submit ("its VAT changed since CARD built it ...
  Rebuild the posting from CARD."). A purchase tax template with several positive rates, or purchase and sales
  templates with different rates, stop the masters setup, the preflight and the preview. Logs written before this
  release have no `vat` key and are compared as before.

Warn only by default (a message, the save goes through):

- **FR-128 — diesel fills on ended equipment.** A new fill, a draft whose company or date changed, or an equipment
  added to a draft, with an equipment of status منتهية, shows "Equipment {0} has status {1}; it should get no new
  diesel fill." and is saved; on submit every equipment is checked again (one message). Only when the company's
  `equipment_status_rule` is "Refuse (equipment status)" is the save or submit refused ("... The equipment status rule
  of company {0} refuses it."). Never stopped: a fill dated on or before the equipment's exit date (else its rental
  end once passed), equipment with status Stopped or Under Maintenance, a project-tank fill without equipment.
  Submitted fills are never re-validated. Verified in `card/equipment_status.py` `check_equipment_status` and
  `project_diesel_fill.py` `_check_equipment_status` at `be73af2`.

### 12.4 Mandatory pre-deploy check (FR-127, read-only)

Run on the target site **before** the deploy, on the code running now. It reads only (`frappe.get_all`,
`frappe.db.get_value`) and ends with `frappe.db.rollback()`; `bench console` also rolls back on exit. It lists, for
every Company, the purchase and the sales tax template of its Card Company Settings row, the number of distinct
positive rates and the rates. It applies the rules of `card.gl.masters._single_template_rate` and
`standard_vat_rate` (distinct positive rates, so two 15% rows on different accounts count as one rate).

Result per company with a Card Company Settings row:

- **FAIL**: a configured template has no positive rate, or more than one distinct positive rate, or belongs to
  another company; the purchase and the sales rates differ.
- **STOP**: the rate is not 15% (the deploy waits until the owner confirms that rate).
- **INFO**: one side (purchase or sales) is not configured while the other is (CARD uses the configured side);
  neither side configured ("no VAT (CARD builds no VAT lines)"); no Card Company Settings row (CARD posts nothing
  for the company).

STOP also sets `RESULT: FAIL`. **If the output ends with `RESULT: FAIL`, the deploy stops**; fix the tax templates in
ERPNext (with the owner's approval) and run the check again.

Command (paste the block into the console, or save it as a file inside the bench container and pipe it in:
`bench --site <site> console < fr127_check.py`). A piped `bench console` ends with the IPython prompt
"Do you really want to exit ([y]/n)?" at the end of the input; it is harmless: answer `y` (nothing was written, and
the console rolls back on exit).

```python
import frappe
from frappe.utils import flt

TEMPLATES = (
	("purchase_tax_template", "Purchase Taxes and Charges Template", "Purchase Taxes and Charges"),
	("sales_tax_template", "Sales Taxes and Charges Template", "Sales Taxes and Charges"),
)
rows = {
	r.company: r
	for r in frappe.get_all(
		"Card Company Settings",
		filters={"parent": "Card Settings", "parenttype": "Card Settings"},
		fields=["company", "purchase_tax_template", "sales_tax_template", "vat_item_tax_template"],
	)
}
result = "PASS"
print("company | field | template | distinct_positive_rates | rates | status")
for company in frappe.get_all("Company", pluck="name", order_by="name"):
	row = rows.get(company)
	if not row:
		print(f"{company} | - | (no Card Company Settings row) | - | - | INFO: CARD posts nothing for it")
		continue
	found = []
	configured = [t for t in TEMPLATES if row.get(t[0])]
	if not configured:
		print(f"{company} | - | (none) | - | - | INFO: no VAT (CARD builds no VAT lines)")
	for field, parent_dt, child_dt in TEMPLATES:
		template = row.get(field)
		if not template:
			if configured:
				print(f"{company} | {field} | (empty) | - | - | INFO: not configured, the other side is used")
			continue
		rates = sorted(
			{
				flt(r)
				for r in frappe.get_all(
					child_dt, filters={"parent": template, "parenttype": parent_dt}, pluck="rate"
				)
				if flt(r) > 0
			}
		)
		owner = frappe.db.get_value(parent_dt, template, "company")
		if owner != company:
			status = f"FAIL: template of company {owner}"
		elif not rates:
			status = "FAIL: no positive rate"
		elif len(rates) > 1:
			status = "FAIL: more than one distinct rate"
		else:
			status = "OK"
			found.append(rates[0])
		if status != "OK":
			result = "FAIL"
		print(f"{company} | {field} | {template} | {len(rates)} | {rates} | {status}")
	if len(set(found)) > 1:
		print(f"{company} | - | - | - | {found} | FAIL: purchase and sales rates differ")
		result = "FAIL"
	elif found and found[0] != 15:
		print(f"{company} | - | - | - | {found[0]:g}% | STOP: not 15%, owner must confirm")
		result = "FAIL"
	vit = row.get("vat_item_tax_template")
	if vit:
		vit_rates = sorted(
			{
				flt(r)
				for r in frappe.get_all(
					"Item Tax Template Detail",
					filters={"parent": vit, "parenttype": "Item Tax Template"},
					pluck="tax_rate",
				)
			}
		)
		print(f"{company} | vat_item_tax_template | {vit} | - | {vit_rates} | INFO")
print("RESULT:", result)
frappe.db.rollback()
```

The last INFO line shows the rates of the linked "CARD VAT" item tax template; a value other than the standard rate
means the next masters setup will create a new "CARD VAT {rate}% - <abbr>" template and the preflight refuses the
old one (section 9). Evidence for the snippet: run on a local throwaway test site only (no Production), with
temporary rows rolled back when the console closed: no Card Company Settings row gave INFO and `RESULT: PASS`;
purchase 15% / sales 5% gave `FAIL: purchase and sales rates differ`; a purchase template with two 15% rows on
different accounts and sales 15% gave `RESULT: PASS`; purchase 15% with sales not configured gave INFO and
`RESULT: PASS`; neither side configured gave "INFO: no VAT"; a template with rates 15% and 5% gave
`FAIL: more than one distinct rate`; purchase and sales 5% gave `STOP: not 15%`; a
purchase template with only a 0% row gave `FAIL: no positive rate`. The temporary rows were
gone after the console closed (rollback). **Partially Verified** (not run on any real site).

### 12.5 Deploy steps

   [DEPLOYMENTS.md](DEPLOYMENTS.md)) and that the platform is frappe 16.55.2 / erpnext 16.54.0.

3. Take a verified backup: `bench --site <site> backup --with-files`; check that the database, public files and
   private files archives exist and have plausible sizes; keep the image or commit of the running version available.

8. Post-deploy checks of section 12.7 (no business record created by the checks); from v4.4.3 also the checks and
   setup actions of [v4.6.0 sections 12.4 and 12.5](v4.6.0.md#124-production-setup-actions-after-the-deploy-each-with-the-owners-approval).

### 12.6 Rollback plan

**Rollback target:** v4.6.0 (`87c375d`, release merge of PR #205; tag `v4.6.0` once published), when the site ran
v4.6.0 before this deploy. If the site goes straight from v4.4.3 to v4.7.0, the target is v4.4.3 (`688eb71`), the
Last Verified Production Deployment: follow [v4.6.0 section 12.6](v4.6.0.md#126-rollback-plan) and add the limits
below. Changes between v4.6.0 and v4.7.0: CHANGELOG [4.7.0] and the PRs of section 2.

**Rules:** checking out an older version restores code only. No rollback, restore or downgrade without the owner's
explicit approval for that action.

**Security effect:** rolling back to v4.6.0 **re-opens the cross-company holes fixed by FR-129**: a company-restricted
user can again create and submit Employee Tool Custody, Equipment Needs Request and Equipment Needs Review records of
another company (and, through a submitted Loss, create that company's draft Material Issue and change its custody
balances). Prefer a forward fix; if a rollback is unavoidable, remove the CARD roles from company-restricted users
until v4.7.x is back.

**Options, in order of preference:**

1. **Forward fix** (default): set `equipment_status_rule` back to "Warn only (equipment status)" for a company that
   chose Refuse (FR-128); align the tax templates (FR-127); or ship a v4.7.x fix.
2. **Code rollback to v4.6.0** (`87c375d`). v4.6.0 code runs on the v4.7.0 database: no column, table or patch was
   added. Before the switch:
   - keep CARD posting on companies whose standard rate is 15% only: v4.6.0 expects 15 and, in its masters setup,
     re-rates the linked "CARD VAT" item tax template to 15 (which changes the VAT of drafts that use it). If a company
     got a "CARD VAT {rate}%" template with another rate under v4.7.0, do not run the CARD masters setup or build
     CARD postings for it on v4.6.0.

   Steps (placeholders only; each step is followed by its check):

   1. Switch the CARD code: deploy the kept v4.6.0 image, or in a bench
      `cd apps/card && git fetch origin && git checkout 87c375d` (or `git checkout v4.6.0` once the tag exists).
      Check: `git -C apps/card rev-parse --short HEAD` shows `87c375d`, and `bench version` lists `card 4.6.0`.
   2. `bench --site <site> migrate`. Check: it ends without an error; the Error Log has no new CARD error.
   3. Restart the web and background workers (`bench restart`, or restart the containers of the image deploy). Check:
      the Desk opens; Card Settings and a Card Monthly Card load.
   4. Record the rollback in [DEPLOYMENTS.md](DEPLOYMENTS.md).
3. **Full restore of the pre-deploy backup**: only when it loses no Production transaction made after the backup, and
   only with the owner's explicit approval for that restore. Switch the code as in option 2 step 1, then
   `bench --site <site> restore <backup-database.sql.gz> --with-public-files <backup-files.tar>
   --with-private-files <backup-private-files.tar>`. Check: the restore and a following `bench --site <site>
   migrate` end without an error; the last document created before the backup is present. Restart the workers and
   record the restore in DEPLOYMENTS.md.

**Data a code rollback does not undo:**

- A "CARD VAT {rate}% - <abbr>" item tax template created by the v4.7.0 masters setup, and its link in the company
  row (only if the rate was not 15).
- The `vat` key in the `built_snapshot` of posting logs built on v4.7.0 (v4.6.0 ignores it: outside the signature).
- On v4.6.0, drafts built under v4.7.0 lose the submit-time VAT check (`check_built_vat`): the `vat` key in their
  `built_snapshot` is ignored, so a VAT change after the build is no longer refused on submit (rebuild such drafts

- Diesel fills saved with a warning (FR-128) stay as saved.
- Removed by a migrate on v4.6.0: the standard Report Equipment Location History (its file is no longer in the app).
  The Card Reports sidebar keeps the link until v4.6.0's sidebar file is re-imported (it is older; remove the link
  by hand if it stays).
