## 4. Improved — Partially Verified

- **Arabic: about eighty CARD messages show in Arabic (PR #351).** `ar.po` gains the CARD-only messages of the GL
  integrity, cash payment, monthly card and supplier statement code. Generic words that frappe, erpnext or hrms
  already translate stay out of `ar.po`, so they keep their own wording site-wide. Display only.
- **Arabic: three words and one status keep HRMS wording on HRMS screens (PR #350).** `card` loads last, so a plain
  `msgid` in `ar.po` replaces the same `msgid` of every other app on the site. `Deductions` (statement column),
  `Workshop` (transport place option) and `Effective from` (operating group member label) move to `msgctxt`
  entries of the CARD DocTypes and reports. The status `Approved` of a cash payment passes the DocType context.
  Display only.
- **The locale guard covers every installed app (PR #350).** `test_no_generic_msgid_overrides` compares `ar.po` with
  every installed app that ships a `locale` folder, not only frappe and erpnext. `main.pot` is generated again with
  the Frappe extractors and merged with the old file (see section 10).
- Verified by CI tests that read the files. Not checked on a Desk in Arabic.

## 5. Fixed — Partially Verified

- **Locking follow-ups of the invoice links and of the monthly build (issue #340, PR #349).** Six points that the
  review of FR-194 and FR-195 left open:
  - **Lock order.** The order is now the same on every path: the invoice row, the source rows in name order, then the
    posting logs. `unlink_customer_invoice` locked the log before the cards. It now locks the cards first.
  - **Wide locks.** The link found the active log of the invoice with a locking read on `posting_doc`, which has no
    index, so it locked rows of other postings. It now reads the name without a lock, locks that row by name, and
    checks its state on the locked row.
  - **Amounts under the locks.** `link_customer_invoice` read the invoice net and the card amounts before the locks.
    It now reads them, and the company, the party, the date and the status, from the locked rows. A credit note
    that is submitted at the same moment can end one of the two transactions as a deadlock. That user repeats the
    action.
  - **Build path.** The monthly build checked the holder of each source with a plain read after the wait. It now uses
    the locking read, so a build that waited for a link is refused and creates no draft invoice with a linked source.
  - **Supplier link and accrual Journal Entry link.** Both read from locked rows and use the same checks and the
    locking holder read. `cards_invoiced` reads Linked logs of both sides without the one-year window, because the
    log of a Linked Purchase Invoice carries the date of the invoice and not the month of the card.
  - **Candidates list.** `unlinked_customer_invoice_candidates` leaves out an invoice in another currency, because the
    link refuses it. The excluded invoices are now conditions of the query, not a growing list of names. Same rows,
    same order, same paging.
  - **Message.** One new message: "{0} changed while it was being linked; try again."
- Verified by 33 CI tests. A value that another transaction commits is simulated by patching the plain reads,
  because one test connection cannot run two transactions. Not run with two real sessions on a site.

## 10. Known Limitations — Verified

- **No index on GL Posting Source (accepted lock scope).** The read that finds the active holder of a source
  (`locked_active_holders`) filters on `source_name` and on the log status, which have no index. It locks the GL
  Posting Source and GL Posting Log rows that it scans until the transaction ends. A link made at the same moment as
  a build or a credit note can wait or end as a deadlock, and the user repeats the action. A narrow lock needs an
  index on GL Posting Source, which is a schema change, so it is a separate decision.
- **A read-only `Workshop` value shows the HRMS or English wording.** Frappe draws a read-only value with the plain
  text, so on a site that has HRMS it does not use the CARD context entry. The editable field shows the CARD Arabic.
- **`card/locale/main.pot` is a union.** It is generated with the Frappe extractors and merged with the old file. 146
  old entries stay by hand because no extractor reads their source (workspace, number card and print format fixtures,
  and strings that left the code). 14 hand-set `msgstr` values stay because a test reads them. A later
  `bench generate-pot-file` run drops these entries, so merge the old file again before a commit.
- **About 132 generic words have no CARD Arabic plain entry, by design.** Frappe, ERPNext or HRMS already translate
  them, and a plain `ar.po` entry would replace that wording on every screen of the site.
- The concurrency tests simulate the second transaction. They are not run with two real sessions.
- Everything listed for v4.14.1 that this page does not change.

## 12. Installation & Upgrade — Partially Verified

- **Upgrade from v4.14.1:** new code; `bench --site <site> migrate`; `bench --site <site> clear-cache`; restart. No
  `bench build` (no `public/` or `frontend/` change). Rebuild the compiled translations, as for every release with
  new messages: the Arabic changes reach a site only with them.
- **Checked from source:** `git diff v4.14.1..HEAD -- card/patches.txt card/patches '*.json' card/hooks.py
  card/fixtures card/public frontend` shows no file. No patch, no DocType JSON, no fixture, no hook, no `public/`
  file and no `frontend/` file changed. The application changes are Python files, one DocType form script and the
  locale files.
- **How the form script reaches users.** `card_cash_disbursement.js` is not an asset file. Frappe adds the file text
  to the form meta of the DocType (`FormMeta.add_code` reads `<doctype>.js` into `__js`,
  `frappe/desk/form/meta.py`, version-16, line 82 and line 93), and the Desk gets that meta when it opens a form
  (`get_meta_bundle`, `frappe/desk/form/load.py`, line 82). In production the form meta is held in the client
  cache under the key `doctype_form_meta::<doctype>` (`frappe/desk/form/meta.py`, lines 32 to 41), and
  `frappe.clear_cache()` empties that cache (`frappe/cache_manager.py`, lines 327 to 328). So the new script needs
  `bench --site <site> clear-cache`, which the upgrade steps already run, and a reload of the Desk in each browser.
  It does not need `bench build`.
- **What migrate writes:** nothing of this release (no DocType, patch, fixture or print format change). **It does not
  write:** any column, document, amount, GL entry, role or permission. No Workspace record is written.
- **Post-deployment acceptance (owner):** reload the Desk once. Open a Card Cash Disbursement in Arabic and check
  that the status shows `معتمد`.
- **Safe rollback — Verified from source; not runtime-tested.** Code only, to v4.14.1, and compile the locale files
  again. No data step.
  - v4.14.2 writes no new field, state or record type. A link, an unlink or a build made on v4.14.2 has the same
    records that v4.14.1 writes, so v4.14.1 reads them without a change.
  - One difference in the data: a supplier link made on v4.14.2 stores the record name of each source. v4.14.1 reads
    that value in the same column.
  - On v4.14.1 code the lock order and the plain reads return, and the Arabic wording returns to the v4.14.1
    wording.
